# app

В этой директории находится бэкенд Fluffy, реализованный на FastAPI. Точкой входа в приложение является `app/main.py`: здесь создается экземпляр FastAPI, регистрируются промежуточное ПО (middleware) и API-маршруты, а также запускаются фоновые задачи для координации WebSocket-соединений на протяжении всего жизненного цикла приложения.

Информацию о настройке всего репозитория можно найти в [корневом файле README](../README.md). Инструкции по запуску сервисов и конфигурации — в [`docs/launch_guide.md`](../docs/launch_guide.md), а руководство по внесению изменений в схему данных — в [`docs/migrations_guide.md`](../docs/migrations_guide.md).

## Краткий обзор архитектуры

Код организован в соответствии с зонами ответственности:

| Директория / файл | Зона ответственности |
| --- | --- |
| `main.py` | Приложение FastAPI, жизненный цикл (lifespan), глобальный обработчик исключений, регистрация маршрутов и middleware |
| `api/v1/endpoints/` | Обработчики HTTP- и WebSocket-эндпоинтов |
| `schemas/` | Pydantic-модели для запросов и ответов |
| `services/` | Сценарии использования (use cases) и бизнес-логика приложения |
| `repository/` | Операции с данными и вспомогательные инструменты для паттерна «единица работы» (unit-of-work) |
| `model/` | ORM-модели SQLAlchemy |
| `core/config.py` | Настройки среды и параметры из `config.yaml` |
| `core/database.py` | Асинхронный движок SQLAlchemy, фабрика сессий, декларативная база моделей |
| `core/redis.py` | Доступ к клиенту Redis |
| `core/celery.py` | Конфигурация приложения Celery |
| `dependencies.py` | Общие зависимости (dependencies) FastAPI |
| `middleware/` | Промежуточное ПО для обработки запросов (включая логирование и ограничение частоты запросов — rate limiting) |
| `infrastructure/` | Внешние интеграции и технические адаптеры: S3, токены верификации, координация WebSocket-соединений, кэширование |
| `tasks/` | Фоновые задачи Celery |
| `exceptions/` | Специфичные для предметной области или интеграций типы исключений |
| `utils/` | Вспомогательные утилиты низкого уровня: работа с JWT, обработка паролей, формирование ответов |

Стандартный поток обработки запроса выглядит так: **эндпоинт → сервис → репозиторий → база данных**. Логику, связанную с HTTP, следует размещать в эндпоинтах, бизнес-правила — в сервисах, а детали взаимодействия с хранилищами данных — в репозиториях или моделях. Доступ к внешним системам должен осуществляться через соответствующие инфраструктурные модули.

## Конфигурация

Настройки загружаются с помощью модуля `app/core/config.py`:

- **`.env`** содержит конфиденциальные данные и параметры подключения к инфраструктуре, включая настройки базы данных, Redis, RabbitMQ, SMTP, S3, а также секретные ключи для JWT.
- **`config.yaml`** содержит неконфиденциальные параметры поведения приложения: например, срок действия токенов, URL-адреса для верификации, режим отладки, время жизни ссылок на аватары и ограничения для WebSocket.

Текущая модель конфигурации требует наличия переменных окружения, указанных в файле .env.example, находящегося в корне проекта.

Используйте `.env.example` в качестве шаблона. Не добавляйте файл `.env` в систему контроля версий (Git) и не указывайте реальные учетные данные в `config.yaml`. URL-адреса для подключений должны быть доступны из того процесса или контейнера, в котором выполняется бэкенд. Для базы данных необходимо использовать асинхронный драйвер (например, `postgresql+asyncpg://...`).

Файл `config.yaml` загружается относительно текущей рабочей директории, поэтому запускайте команды из корневой папки репозитория (если только вы намеренно не задали другую рабочую директорию).

## Локальный запуск API

Для для локального запуска API достаточно выполнить команду:

```bash
docker compose --profile prod up --build
```

Все настроенные инфраструктурные компоненты должны быть доступны. Механизм `lifespan` в FastAPI выполняет проверку соединения с Redis при запуске приложения. Инструкции по полному циклу работы с Docker и запуску фронтенда можно найти в руководстве по запуску (launch guide).

## База данных и миграции

Модели ORM находятся в директории `model/`, а метаданные Alembic и импорты моделей — в файле `../migrations/env.py`. После внесения изменений в модель создайте миграцию (находясь в корне репозитория) и обязательно проверьте её содержимое:

```bash
alembic revision --autogenerate -m "описание изменений схемы"
alembic upgrade head
```

Никогда не полагайтесь на то, что автоматически сгенерированная миграция верна — всегда проверяйте её. См. [руководство по миграциям](../docs/migrations_guide.md).

## Инженерные соглашения

- Обработчики эндпоинтов (endpoint handlers) должны быть максимально лаконичными; бизнес-логику следует выносить в сервисный слой (services).
- Используйте схемы (schemas) для валидации входных и выходных данных API; не возвращайте объекты ORM напрямую.
- Операции с базой данных должны выполняться в репозиториях (repositories) с использованием паттернов асинхронных сессий (async session) и «единицы работы» (unit-of-work).
- Явно обрабатывайте сбои внешних сервисов; используйте для этого существующие модули исключений.
- При изменении логики сервисов, механизмов аутентификации, работы с данными или системы обмена сообщениями в реальном времени — добавляйте или обновляйте соответствующие тесты.
- Вносите изменения в схему данных только через новые, проверенные миграции Alembic; не изменяйте уже примененные миграции для отражения новых правок.
- Никогда не выводите в логи секретные данные, токены доступа, пароли или проверочные коды.
